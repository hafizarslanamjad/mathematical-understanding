Chapter 1 — Two Ways of Describing a Computation

How one computational task can be expressed through instructions, programming abstractions, and mathematical relationships.

1.1 The Same Task Can Be Described in Different Ways

Suppose we have three item prices:

10, 25, 15

We want to find the total price. Before thinking about Python or mathematical notation, we can perform the calculation directly:

10 + 25 + 15 = 50

The task is simple: take the three prices and combine them through addition. The input is the collection \(10,25,15\), and the output is \(50\).

Now let us write a Python program that performs this task:

prices = [10, 25, 15]

total = 0

for price in prices:
    total = total + price

To understand exactly what this program does, we can follow it one step at a time. Before the loop begins, total is initialized to zero:

total = 0

During the first iteration, price is 10, so the program calculates:

total = 0 + 10 = 10

During the second iteration, price is 25:

total = 10 + 25 = 35

During the third iteration, price is 15:

total = 35 + 15 = 50

The loop reaches the correct answer by describing a sequence of actions. This is one way of describing the task. Python allows us to describe the same task differently:

prices = [10, 25, 15]
total = sum(prices)

This program does not show us the intermediate totals 10, 35, and 50. It simply says: compute the sum of the values in prices. The detailed repetition still has to happen somewhere inside Python, but those details are hidden from the person reading the code. We can also describe the task mathematically:

\[ 10+25+15=50. \]

If we want a description that works for any number of prices, we can name them \(p_1,p_2,\ldots,p_n\) and write:

\[ T=\sum_{i=1}^{n}p_i. \]

The symbols may initially look more difficult than the Python loop, so let us connect every symbol to the concrete example. In our collection, there are three prices, so \(n=3\). The prices are:

\[ p_1=10,\qquad p_2=25,\qquad p_3=15. \]

The symbol \(T\) represents the total. Substituting the concrete values into the equation gives:

\[ T=p_1+p_2+p_3 \]

and therefore:

\[ T=10+25+15=50. \]

We now have four descriptions before us:

Direct calculation:       10 + 25 + 15 = 50
# Explicit loop
total = 0

for price in prices:
    total = total + price
# Built-in Python operation
total = sum(prices)

\[ T=\sum_{i=1}^{n}p_i. \]

These descriptions do not look the same, but they express the same central task: combine all the prices through addition to obtain their total. The task itself is what we will call the computation. In this example, the computation is:

Transform a collection of prices into one value by adding all the prices.

The loop, sum(prices), and the mathematical summation are different representations of that computation. A representation is simply a particular way of expressing something.

In our price example, the representations reveal different information. The loop reveals the individual actions performed during the process. It shows the total changing from 0 to 10, then to 35, and finally to 50. This is useful when we are learning how accumulation works or when we need to inspect what happens during each iteration. The loop also has a cost: the reader must mentally simulate several steps before seeing the complete relationship.

The advantage of expression sum(prices) is that it names the complete operation directly. A reader familiar with sum immediately knows that all the prices are being added. Its disadvantage is that it hides how the result is constructed.

The mathematical expression says that \(T\) is obtained by adding every price from the first price to the \(n\)th price. This form is useful because it is independent of Python. The same relationship could be implemented in Python, C++, Java, a spreadsheet, a database, or a calculator. However, the equation does not specify important programming details such as where the prices are stored, which data type they use, or how the computer should react if the collection contains invalid data.

There is another important consequence. Once we understand that a computation can have multiple representations, we are no longer forced to accept the first implementation that comes to mind. We can ask whether another representation makes the task easier to understand, verify, generalize, or execute.

No representation is automatically the best in every situation. If we are teaching how an accumulator changes, the loop may be best. If we are writing ordinary Python and only need the total, sum(prices) may be clearest. If we are analyzing an algorithm or connecting the task to statistics, the mathematical equation may be most useful. The choice depends on what we need the representation to reveal.

This book will train us to move between such descriptions. We will begin with concrete values and ordinary code because they let us observe what actually happens. We will then search for the larger relationship formed by those operations. Finally, we will give that relationship a mathematical expression and translate it back into code.

1.2 The Relational View

Consider the following scores:

scores = [40, 70, 55, 30, 75]

We want to calculate the average of the passing scores, where a score is considered passing when it is at least 50.

A familiar Python solution is:

total = 0
count = 0

for score in scores:
    if score >= 50:
        total = total + score
        count = count + 1

average = total / count

We can understand this program by following its execution. The program begins with total = 0 and count = 0. It visits 40, rejects it, visits 70, adds it to total, increases count, and continues in this manner until every score has been examined. This explanation tells us how the program reaches its result. Now let us temporarily set the execution steps aside and look directly at the input. The original scores are:

40, 70, 55, 30, 75

The passing scores are:

70, 55, 75

Their total is:

\[ 70+55+75=200, \]

and there are three of them. Their average is therefore:

\[ \frac{70+55+75}{3}=\frac{200}{3}. \]

This second explanation does not begin with total, count, or the order in which the loop visits the scores. It begins by identifying the quantities that belong in the result and then states the relationship among them:

The required result is the sum of the passing scores divided by the number of passing scores.

The program and this statement concern the same problem, but they organize our attention differently. The program directs our attention toward the process: initialize, visit, test, update, and repeat. The second description directs our attention toward the relationship between the complete input and the required output.

This is the relational view of computation. Instead of asking primarily,

What instruction should execute next?

we ask:

Given the input, what must be true of the output?

The Output Depends on the Input in a Particular Way

Let us examine a simpler example before generalizing this idea. Suppose a store sells notebooks for 120 rupees each. The following table shows the total cost for several quantities:

Number of notebooks Price of one notebook Total cost
1 120 120
2 120 240
3 120 360
5 120 600

Each row contains different input and output values, but the same relationship connects them. If \(n\) represents the number of notebooks, \(p\) represents the price of one notebook, and \(C\) represents the total cost, we can write:

\[ C=np. \]

The equation \(C=np\) does not describe a sequence such as “read n, read p, multiply them, create C, and store the result.” A computer implementation must eventually perform operations, but the equation concentrates on a different fact: for every permitted pair of values \(n\) and \(p\), the total cost \(C\) must equal their product.

A Python program can realize this relationship directly:

number_of_notebooks = 5
price_per_notebook = 120

total_cost = number_of_notebooks * price_per_notebook

A more procedural program could realize it through repeated addition:

number_of_notebooks = 5
price_per_notebook = 120
total_cost = 0

for _ in range(number_of_notebooks):
    total_cost = total_cost + price_per_notebook

For the given input, both programs produce:

600

Their instructions differ, but the required relationship remains:

\[ C=np. \]

This relationship gives us a standard against which implementations can be judged. If a program receives \(n=5\) and \(p=120\) but produces \(720\), it has not realized the required relationship.

The relational view therefore separates two questions:

  1. What result is required for a given input?
  2. What instructions will produce that result?

The first question determines the meaning that must be preserved. The second determines how that meaning will be implemented.

Inputs and Outputs Have Roles, Not Merely Values

Consider the following calculation:

\[ 5\times120=600. \]

Suppose that the number 5 represents a quantity of notebooks, while 120 represents rupees per notebook. Although both are written as numbers, they do not play interchangeable roles in our interpretation. We can record their meanings explicitly:

5 notebooks × 120 rupees per notebook = 600 rupees

The unit “notebooks” combines with “rupees per notebook”: \[ \text{rupees}. \]

The notebook units cancel, leaving rupees: \[ \text{rupees}. \]

This unit relationship helps explain why multiplication is appropriate. Each notebook contributes 120 rupees, and \(n\) notebooks contribute \(n\) copies of that amount. The equation preserves not only numerical values but also the meanings attached to them.

Now suppose a programmer accidentally writes:

total_cost = number_of_notebooks + price_per_notebook

For five notebooks at 120 rupees each, this produces:

125

The error is not merely that 125 is the wrong number. Addition expresses the wrong relationship. It treats the number of notebooks and the number of rupees per notebook as quantities that should be combined directly:

5 notebooks + 120 rupees per notebook

Those quantities do not form a total price through addition. The relational view helps us detect the mistake before or independently of tracing the program. This habit is central to mathematical programming. We do not begin by searching our memory for an operator that appears in similar code. We ask what role each quantity plays and what relationship must hold among those roles.

The Relational View Helps Compare Different Programs

Consider two possible implementations:

# Program A
total = 0
count = 0

for score in scores:
    if score >= 50:
        total = total + score
        count = count + 1

average = total / count
# Program B
passing_scores = []

for score in scores:
    if score >= 50:
        passing_scores.append(score)

average = sum(passing_scores) / len(passing_scores)

Their intermediate states differ. Program A stores a running total and count. Program B constructs a new list. Nevertheless, for the input:

[40, 70, 55, 30, 75]

both produce:

\[ \frac{200}{3}. \]

Why can we call them two implementations of the same computation? It is not because their instructions are identical. They are not. We regard them as equivalent for this problem because they establish the same required input-output relationship:

For a collection containing at least one passing score, return the arithmetic mean of all scores greater than or equal to 50.

This statement also exposes an assumption that the code may not initially make obvious: there must be at least one passing score. Consider:

scores = [20, 35, 40]

There are no passing scores, so both programs eventually attempt division by zero. The required relationship is not currently defined for this input because the “number of passing scores” is zero: \[ \frac{0}{0}. \]

The relational view encourages us to specify constraints on inputs. We must decide what the program should do when no passing scores exist. It might return None, raise an error, or use another explicitly chosen convention. Until that decision is made, the computation is only defined for collections containing at least one passing score.

What the Relational View Makes Easier to See

The notebook example makes the required dependency visible:

\[ C=np. \]

The score example makes the complete selection-and-average structure visible: \[ \frac{\text{sum of passing scores}} {\text{number of passing scores}}. \]

From these examples, we can identify several concrete strengths of relational reasoning.

First, it makes the intended output easier to verify. If five notebooks cost 120 rupees each, any correct program must produce 600 rupees. If a program produces 125, the relationship immediately exposes the error.

Second, it supports generalization. The calculation \(5\times120=600\) concerns one purchase, while \(C=np\) describes every purchase governed by the same pricing rule.

Third, it reveals the roles of quantities. The value 5 is not merely a number; it is a number of notebooks. The value 120 is a price per notebook. Their roles explain why multiplication produces a total measured in rupees.

Fourth, it permits comparison between different implementations. Two score-processing programs can use different intermediate data and still realize the same relationship between the input scores and the output average.

Fifth, it exposes assumptions. The passing-score average requires at least one passing score. Writing the relationship as a division makes the zero-denominator problem visible.

Each strength comes from focusing on what must remain true across implementations rather than on the particular instructions used by one implementation.

What the Relational View Can Leave Hidden

The relational view does not make every important feature of a program visible. Consider two bank transactions applied to an account with a balance of 100 rupees:

deposit 50
withdraw 130

If the deposit happens first, the balance changes as follows:

100 → 150 → 20

If the withdrawal happens first and the bank rejects withdrawals larger than the current balance, the result is different:

100 → withdrawal rejected → 150

Simply adding the numerical changes,

\[ 100+50-130=20, \]

describes the final balance only under rules that allow both transactions to occur. It does not represent the rejection rule or show that transaction order can affect which actions are permitted.

In this situation, the history matters. The current balance at the moment of withdrawal determines whether the withdrawal occurs. A description concerned only with the initial and final numbers may hide that dependency.

Side effects create a similar issue. The two instruction sequences

save_order()
send_confirmation_email()

and

send_confirmation_email()
save_order()

contain the same two actions but may not be equivalent. If saving fails, the second sequence may send confirmation for an order that was never stored. A simple relationship between input and return value may not capture this externally visible difference.

1.3 Finding the Relationship Inside a Program

The central skill required for mathematical programming is the ability to begin with ordinary code and determine what the complete collection of instructions means. Consider the following program:

values = [2, -3, 4]

total = 0

for value in values:
    total = total + value * value

Suppose we do not yet know the mathematical expression represented by this loop. We can begin with the concrete values and execute the program:

Current value value * value Previous total New total
2 4 0 4
-3 9 4 13
4 16 13 29

The final result is 29. Merely knowing the result, however, does not tell us the general relationship represented by the program. Therefore, we should start by asking what each instruction contributes to that result. During the first iteration, the program contributes:

\[ 2\times2=2^2=4. \]

During the second iteration, it contributes:

\[ (-3)\times(-3)=(-3)^2=9. \]

During the third iteration, it contributes:

\[ 4\times4=4^2=16. \]

The variable total combines these contributions through addition:

\[ 4+9+16=29. \]

Substituting the original values back into this expression gives:

\[ 2^2+(-3)^2+4^2=29. \]

We have now moved beyond saying that the program “uses a loop.” The loop is only the mechanism that repeats the instructions. The complete computation is:

Square every value and add the squared values.

This sentence exposes two different structures hidden inside the loop:

  1. Each individual value is transformed into its square.
  2. All the transformed values are combined through addition.

From Concrete Positions to Indexed Values

The expression

\[ 2^2+(-3)^2+4^2 \]

describes our iterating over a particular length of list. We now want to describe the same computation for a list of any length. Let the input values be:

\[ x_1,x_2,\ldots,x_n. \]

Here, \(x_1\) represents the first value, \(x_2\) represents the second value, and \(x_n\) represents the final value in a collection containing \(n\) values. Now, the general form of contribution made by the first value is:

\[ x_1^2. \]

The contribution made by the second value is:

\[ x_2^2. \]

Continuing in the same way, the complete result is:

\[ x_1^2+x_2^2+\cdots+x_n^2. \]

Summation notation provides a compact representation of this repeated addition:

\[ S=\sum_{i=1}^{n}x_i^2. \]

Every part of the notation corresponds to something already visible in the concrete program:

The Accumulator Reveals the Combination Rule

The initial value of an accumulator often gives us an important clue about the relationship being constructed. In the sum-of-squares program, the accumulator begins at zero:

total = 0

and each contribution is added:

total = total + value * value

Zero is appropriate because adding zero does not change the value being added in zero itself:

\[ 0+a=a. \]

If the first squared contribution is \(4\), beginning with zero gives:

\[ 0+4=4. \]

The initialization allows the same update rule to be used during the first iteration and every later iteration. Now consider a different program:

values = [2, 3, 4]

product = 1

for value in values:
    product = product * value

Its execution is:

Current value Previous product New product
2 1 2
3 2 6
4 6 24

This accumulator begins at one rather than zero because the contributions are combined through multiplication:

\[ 1\times a=a. \]

Beginning at zero would destroy the product immediately:

\[ 0\times2\times3\times4=0. \]

The program represents:

\[ 2\times3\times4=24, \]

or generally:

\[ P=\prod_{i=1}^{n}x_i. \]

Separate the Per-Element Transformation from the Combination

Consider another loop:

values = [2, -3, 4]

total = 0

for value in values:
    contribution = 2 * value + 1
    total = total + contribution

Let us trace it:

\(x\) Contribution \(2x+1\) Previous total New total
2 5 0 5
-3 -5 5 0
4 9 0 9

The program performs two conceptually different operations. First, it transforms each value:

\[ x\longmapsto2x+1. \]

For the concrete input, this transformation produces:

[2, -3, 4] → [5, -5, 9]

Second, it adds the transformed values:

\[ 5+(-5)+9=9. \]

The complete relationship is therefore:

\[ S=\sum_{i=1}^{n}(2x_i+1). \]

The parentheses are important. They show that the entire expression \(2x_i+1\) is the contribution associated with the \(i\)th input value. The summation then combines all such contributions. This distinction between transforming and combining is useful because many loops have this structure:

accumulator = initial_value

for item in collection:
    contribution = transform(item)
    accumulator = combine(accumulator, contribution)

The concrete questions are:

What does one item become?
How are the resulting contributions joined?

Not Every Loop Produces One Accumulated Value

Now consider:

values = [2, -3, 4]
transformed_values = []

for value in values:
    transformed_values.append(2 * value + 1)

The concrete execution produces:

[2, -3, 4] → [5, -5, 9]

Unlike the earlier program, this loop does not add the transformed values. It preserves each transformed value in a new collection. We can express the relationship between corresponding input and output positions as:

\[ y_i=2x_i+1. \]

For the concrete list:

\[ \begin{aligned} y_1&=2(2)+1=5,\ y_2&=2(-3)+1=-5,\ y_3&=2(4)+1=9. \end{aligned} \]

The earlier program computed one number:

\[ \sum_{i=1}^{n}(2x_i+1). \]

The current program computes a collection:

\[ [y_1,y_2,\ldots,y_n], \qquad y_i=2x_i+1. \]

This example shows why identifying only the per-element expression is insufficient. We must also inspect what the program does with each result. Compare the two final instructions:

total = total + contribution

and:

transformed_values.append(contribution)

The first collapses many contributions into one accumulated value. The second constructs a new collection containing one output for every input. We can now recognize two broad structural patterns:

Structural pattern Concrete behavior Result shape
Transform each element [2, -3, 4] → [5, -5, 9] Many values become many values
Combine contributions [4, 9, 16] → 29 Many values become one value

Later, these patterns will be connected to vector operations, mapping, reductions, NumPy, and tensor programming. At this stage, their importance is simpler: two loops may both visit every element while representing fundamentally different relationships.

Conditions Determine Which Values Contribute

Consider a third kind of loop:

values = [4, -2, 7, -5, 3]

total = 0

for value in values:
    if value > 0:
        total = total + value

The execution can be organized by asking whether each value contributes to the total:

Value Is it positive? Contribution
4 Yes 4
-2 No Nothing
7 Yes 7
-5 No Nothing
3 Yes 3

The values that contribute are:

4, 7, 3

and the final result is:

\[ 4+7+3=14. \]

The complete relationship can currently be stated in words:

Add all values in the input collection that are greater than zero.

The condition does not merely control whether one line executes. From the relational view, it determines membership in the collection of contributing values.

At this point, we can identify the selection relationship verbally, but we have not yet constructed a compact algebraic expression for it. How can the condition value > 0 itself become part of a mathematical expression? How can a value contribute when the condition is true and disappear when the condition is false?

Those questions require the next major idea of the book: treating Boolean conditions as mathematical objects. We will develop that idea carefully rather than inserting a completed formula here without explaining where it comes from.

However, In this section, we have learnt to decompose the code into four semantic roles:

item
condition
contribution
combination

Not every program will contain all four roles. A loop without a condition allows every object to contribute. A transformation that constructs a new list may preserve each contribution rather than combining them. Nevertheless, these questions help us locate the structure before choosing mathematical notation.

Translating in the Reverse Direction

The translation process must also work from mathematics back to code. Suppose we are given:

\[ S=\sum_{i=1}^{n}x_i^2. \]

Before writing Python, we can unpack the expression.

The symbol \(i=1,\ldots,n\) tells us that every input position is involved. The expression \(x_i^2\) tells us the contribution associated with one input value. The summation symbol tells us that these contributions are combined through addition. The symbol \(S\) names the final result. This interpretation leads naturally to:

total = 0

for value in values:
    contribution = value * value
    total = total + contribution

Now consider:

\[ y_i=2x_i+1. \]

The subscript \(i\) appears on both \(x\) and \(y\). This tells us that every input position has a corresponding output position. The expression does not sum the outputs. It defines each output separately:

transformed_values = []

for value in values:
    transformed_values.append(2 * value + 1)

This is why learning mathematical programming cannot consist only of memorizing Python replacements. The notation expresses the organization of the computation. To translate it correctly, we must understand which objects exist, what happens to one object, and how the individual results are organized.
